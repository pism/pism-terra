## [1.0.0]

### Added
- The ERA5 forcing (`climate.era5`) carries `air_temp_sd`, the standard deviation of the daily-mean 2-m temperature within each month, as the CARRA2 forcing does. The monthly means it is built from hold no day-to-day variability, so `climate.era5_air_temp_sd` downloads daily means from `derived-era5-single-levels-daily-statistics` -- one request per year, on a box padded by one degree -- takes the population standard deviation per month (as `cdo monstd` does for CARRA2) and resamples it onto the ERA5-Land grid. The global 0.25 degree product is used rather than ERA5-Land's because it is defined over water. A month the download lacks is an error rather than a NaN.
- `prepare_carra2` downloads CARRA2's snowfall (`time_integral_of_total_solid_precipitation_flux`, the solid part of `total_precipitation` in the same monthly forecast-based product) and writes it to the store as `snowfall` in kg m^-2 day^-1, treated exactly like `precipitation`. It is requested on its own, so the precipitation already downloaded is reused. Nothing downstream of the store names its variables, so the monthly climatology, the per-group files and the per-glacier files carry it without further changes. Yearly batches and a store that predate it are rebuilt on the next run (`climate.has_variables`); the climatology and per-group files derived from the store need `--force-overwrite`.
- The PISM-Cloud apps (`notebooks/pism_cloud_glacier_app.ipynb`, `notebooks/pism_cloud_ismip7_app.ipynb`) connect with the Earthdata login saved in `~/.netrc`, which is where `earthaccess.login(persist=True)` puts it, when the user and password fields are left blank. The connect step names the saved user, and the result line says who is connected. Typed credentials are used as before.
- `pism-ismip7-greenland-prepare` has a `regional_grids` step that writes one regional grid file per glacier of `pism_terra/data/mouginot_glaciers_w_shelves.gpkg` (246 glaciers) to `<OUTPUT_PATH>/input/grids/pism_{NAME}_grid.nc`, so they are uploaded with the other inputs and a campaign uses one with `grid_file = "pism_{NAME}_grid.nc"`. The domain is the bounding box of the outline plus a 3 km buffer, snapped to the 150 m grid of `GreenlandObsISMIP7-v1.3.nc` and grown about its centre with `pism_terra.domain.get_bounds` to a multiple of 216 km, the least common multiple of the resolutions of the ice-sheet-wide domain (150 m times 1, 2, 3, 4, 5, 6, 8, 9, 10, 12, 16, 18, 20, 24, 30, 32). Only the axes of the observation file are read, from a local copy or by byte ranges from `s3://pism-cloud-data/obs/`. The setup's `[regional_grids]` table sets the outlines, the name column, the buffer and the resolutions (`pism_terra.ismip7.greenland.prepare.regional_bounds`, `prepare_regional_grids`). `pism_terra.aws.download_from_s3` now creates the directory of its destination.
- Grid files live in the `grids` subdirectory of the ISMIP7 Greenland inputs, locally and in the bucket (`s3://{bucket}/{prefix}/{version}/grids/`). `pism-ismip7-greenland-prepare` writes `pism_bedmachine_greenland_grid.nc` to `<OUTPUT_PATH>/input/grids/` beside the regional grids, and `pism-qaamerujup-prepare` writes `pism_qaamerujup_grid.nc` there. Campaign configs do not change: `grid_file` still names the file only, and `pism-ismip7-greenland-stage` (and so the run generators) looks for it under `grids/` (`pism_terra.ismip7.greenland.stage.select_grid_file`). A grid file that is only beside the other inputs, as uploaded before this layout, is still staged from there, with a note; a `grid_file` that carries a directory is used as written.
- `python -m pism_terra.glacier.render_terrain_3d --outlines FILE` animates dated outlines. When the file has a date column (`--outline-time`, found automatically as `Date`, `date`, `time` or `datetime`), each frame draws, for every glacier (`--outline-group`, found automatically as `GlacierID`, `glacier_id`, `rgi_id` or `RGIId`), the latest outline observed up to the frame's model time. `--outline-max-age DAYS` drops fronts that have not been replaced for that long, and `--outline-time none` keeps the old static drawing. Line features are now drawn as they are; before, only their endpoints survived and nothing was drawn.
- The `calfin` step of `pism-ismip7-greenland-prepare` also downloads CALFIN's Greenland-wide calving-front lines (`termini_1972-2019_Greenland_lines_v1.0.shp`, dated `Date`, numbered `GlacierID`) into `<OUTPUT_PATH>/calfin/`, next to the polygons the retreat masks are built from (`pism_terra.ismip7.greenland.forcing.download_calfin`). They are what `render_terrain_3d --outlines` animates.
- `pism-qaamerujup-prepare pism_terra/config/setup_qaamerujup.toml OUTPUT_PATH` sets up the Qaamerujup regional domain for `pism-ismip7-greenland-run-*` (`qaamerujup_century.toml`), replacing the pism-ragis notebook. It writes three files into `OUTPUT_PATH/input`, to be uploaded next to the ISMIP7 Greenland inputs (`ismip7/greenland/input/v3`), whose forcing, heat flux and regrid state the runs use as they are:
  - `grids/pism_qaamerujup_grid.nc`: the extent of `domain_qaamerujup.gpkg`, grown to tile 32, 64, 96 and 128 m. The gpkg is labelled EPSG:4326 but holds EPSG:3413 coordinates, which `read_outline` detects and mends.
  - `boot_1931_qaamerujup.nc` (32 m): the reconstructed 1931 surface inside the buffered outline and ArcticDEM outside it, with the gaps between them filled by a Laplace solve. The bed and mask come from the ISMIP7 observation dataset, read only in the domain's window. Thickness is surface minus bed inside the 1931 outline and follows the mask elsewhere, so the two DEMs no longer put ice on land. The exclusion polygon becomes deep ocean, and `ftt_mask` holds the geometry outside the buffered outline.
  - `obs_1931_qaamerujup.nc`: velocities and inversion masks.

  The raw inputs are read from `s3://pism-cloud-data/qaamerujup/` (or `--data-path`). The obs file is built by `pism_terra.ismip7.greenland.forcing.inverse_observations` / `write_inverse_observations`, now shared with the ice-sheet `prepare_observations`.
- Configs take a `[regional]` section, passed through to every PISM leg of every runner like `[fracture_density]`. `'regional' = ""` adds PISM's `-regional` flag (regional mode is on whatever its value), and the `regional.*` options set the no-model strip and its boundary conditions. `qaamerujup_century.toml` runs in regional mode with a 0.32 km no-model strip and zero-gradient boundary conditions. Multi-rank regional runs need PISM with pism/pism#583, which fixes a deadlock while writing the model state.

The sections are written in Markdown (`paper/sections/`), converted with pandoc and compiled into the Copernicus template (`paper/main.tex`, package 7.16 in `paper/copernicus/`) by `make`; `make figures` runs the case-study pages with jupytext to make the figures. `paper/BUILD.md` lists every step.

(2021), and its config `pism_terra/config/gmd_case_study_1_glacier.toml`. The figures are made from the run's small postprocessed products, read from `PISM_TERRA_PAPER_DATA`.
- ISMIP7 Greenland runs take `campaign.retreat_file = "none"` (or no `retreat_file`) to run without a prescribed front: staging fetches and checks no mask, and every leg leaves `geometry.front_retreat.prescribed.file` and `.periodic` off the PISM command line, which is how PISM turns the prescribed retreat off (it would try to open a file called `none`). Before, `"none"` was staged as a file name and the run could not start.
- `python -m pism_terra.glacier.render_terrain_3d --particles N` animates the surface flow on top of the rendering: N particles are advected through `uvelsurf`/`vvelsurf` (midpoint steps, linear interpolation; per-second units are converted) and drawn as trails that fade toward their tails, draped just above the ice. One frame advances them by `--particle-step` years of flow (by default the 95th-percentile ice speed moves one grid cell per frame), and they respawn at random on moving ice after `--particle-life` frames, off the ice, or below `--particle-min-speed`. `--particle-trail`, `--particle-color`, `--particle-width` and `--particle-seed` set the look. The particles are traced once before rendering, so `-j` still renders frames in parallel.
- `pism-inverse-lcurve` and `pism-inverse-plot` take an ensemble that samples the inversion strategy, the value of `inverse.design.variable` (`tauc`, `hardav`, or the alternating pairs `tauc_hardav` and `hardav_tauc`), together with the penalty weight, so one project gives all four L-curves. `pism-inverse-lcurve` draws one curve per strategy on shared axes, with the norm summed over a pair's phases, `N = sqrt(J_tauc + J_hardav)` (each `J_design` measures the departure of zeta from its prior, so a single field adds nothing for the other), writes one table row per member, and adds a phase figure per pair (`lcurve_tauc_hardav.png`, `lcurve_hardav_tauc.png`). `pism-inverse-plot` gives every field figure one row of panels per strategy that inverted for it and one column per weight. Both take `--strategy` to keep a subset. The S4F inversion docs page and `docs/make_data/s4f_inversion_figures.py` now follow the single project `2026_10_inverse_lcurve` run with `s4f_inverse_calib.toml` and a factorial `inverse_penalty.toml`.
- `python -m pism_terra.glacier.render_terrain_3d` takes Crameri's scientific colormaps for `--base-cmap` and `--overlay-cmap`, as `batlow` or `cmc.batlow` (and `_r` for reversed). The prefix picks Crameri's version where matplotlib has a map of the same name (`berlin`, `managua`, `vanimo`).
- `python -m pism_terra.glacier.render_terrain_3d` shades the relief like a GIS hillshade: a multidirectional hillshade of the terrain (`--shading multidirectional`, the default, or `hillshade` for one light; `--light-azimuth`, `--light-altitude`, `--hillshade-exaggeration`) is multiplied into the colors of both layers, so the shading no longer depends on the camera. The elevation colormap is faded toward white by `--base-tint` (0.4) so the relief reads through it, and the overlay on ice is drawn with `--overlay-opacity` (0.85). `--shading lit` gives the previous rendering with PyVista's lights.
- `python -m pism_terra.glacier.render_terrain_3d --pan X Y` shifts the picture right and up by fractions of the frame height, to recentre a terrain that the camera angle pushes toward one edge.

The x-axis label of the step and phase figures now wraps onto two lines so it is no longer cut off.

- `pism_terra.ismip7.greenland.mass_balance.plot_region` draws one basin (the ice sheet by default) in one panel: every (GCM, pathway) cumulative mass balance over the Mankoff band, both zeroed at `sle_reference` (2015), with the contribution to sea level since then in mm SLE on a right-hand axis (1 mm SLE = 362.5 Gt, converted with pint by `to_sea_level`). It accepts a dataset already reduced to that basin. `pism-ismip7-greenland-mass-balance` writes it as `greenland_mass_balance.png` next to the per-basin figure.
- `python -m pism_terra.tools.gl_flux_mask_diagnosis RUN_A RUN_B --labels A,B` compares the grounding-line flux (`ice_mass_transport_across_grounding_line`) of two runs that differ in their front-retreat mask. Per ISMIP region it gives the time-weighted flux and budget, whether the flux goes into floating or ice-free ocean cells, and the grounded cells at the grounding line (count, thickness, speed, and `rho H u dx`), so a difference splits into length, thickness and speed. It reads both retreat masks from the runs' `command`, puts them on the run grid as PISM does, and reports how much of the difference lies next to cells whose mask class (none, partial, full) differs. The 9 km tiles with the largest differences get coordinates and zoom maps.
- `notebooks/pism_cloud_progress_app.ipynb`, a Voila app to check in on a project's PISM-Cloud runs later, without the notebook that submitted them: given the Name, Project and Bucket of the ISMIP7 and glacier apps it lists every job id under `s3://{bucket}/{name}/{project}/` anonymously, labels each by its run script (or, while an execute job is still running and has mirrored nothing but its log, by the output directory the log names), shows when each log was last published and how far through its time span the run is, and follows a chosen job's live log with the same progress bar as the other apps.
- `pism-ismip7-greenland-mass-balance [--root DIR|s3://…] OUTPUT_PATH` opens an ISMIP7 submission tree, in the cloud bucket or on disk, as one lazy ensemble on `(gcm_id, ssp_id)`, integrates the surface, basal and grounding-line fluxes over the Mouginot basins in a single Dask pass (one `xr.dot` against the stacked basin masks rather than a masked sum per basin), builds the regional mass balance and its cumulative series, and plots them per basin against the staged Mankoff product. Progress bars cover the file check and the integration; `pism_terra.ismip7.greenland.mass_balance` exposes each step for notebooks, and `notebooks/ismip7_cloud_plot.py` walks through them.
- `pism-ismip7-greenland-importance-sampling-dh` pairs every observed record with the nearest model step within `--time-tolerance` (183 days by default) instead of joining on identical dates: PISM stamps spatial output at the middle of each reporting interval, so a monthly series never lands exactly on the 2019-01-01 the Smith product is dated. It also takes `thk` as thickness, beside `lithk`, so the dh of a plain run's `thk` is compared without the surface-elevation caveat.
- `pism-ismip7-greenland-stage` and the ISMIP7 run generators copy the observed thickness change named by `campaign.dh_files` into `<output-path>/output/observations/`, beside the GRACE and Mankoff products, so `pism-ismip7-greenland-importance-sampling-dh` finds every observation in one place (`pism_terra.ismip7.greenland.observations.place_files`).
- `pism-ismip7-greenland-importance-sampling-flux RUN_DIR OUTPUT_PATH [--variable mass_balance] [--freq YS] [--start] [--end] [--fudge-factors 1,3,10]` importance-samples an ISMIP7 Greenland UQ ensemble against the Mankoff et al. (2021) mass fluxes, region by region: the per-member `region_*.nc` flux series of `pism-ismip7-postprocess-flux` and the staged observations are averaged onto the same calendar bins (`MS|ME|YS|YE`), the bins either record only partly covers are dropped, and a Gaussian likelihood on the chosen flux runs over the sampling window for every fudge factor. Per region it writes a flux figure (observed, prior and posterior 5-95 % bands of the mass balance, surface mass balance and grounding-line flux, sampling window shaded), a posterior histogram of the `uq.csv` parameters, tables and a NetCDF file; the basins' log-likelihoods are summed into a joint posterior. `pism_terra.calibration.weighted_quantiles` gives the posterior bands.
- The importance-sampling tools show progress on a terminal: a bar over the glaciers, regions or observed products, and Dask progress for the reductions over an ensemble (`pism_terra.progress`: the distributed bar when a `dask.distributed.Client` is active, the local `ProgressBar` otherwise, and neither when the output is not a terminal). The fudge factors of `pism_terra.calibration.importance_weights` are now evaluated in one pass over the ensemble instead of one per factor.
- `pism-profile-analysis PATHS... --output-path OUT` reads the `-profile` files of one or more runs and reports how much of the time-stepping loop the Blatter solve costs next to PISM's other components, then breaks the solve down into its Newton-step phases (residual, Jacobian, preconditioner setup, linear solve, line search) and linear-algebra kernels, each with mean, slowest and fastest rank, plus iteration counts (Newton per step, GMRES per Newton, Jacobian assemblies per Newton) and seconds per rank for the assembly and scatter events. CSVs, four figures (crameri's batlowS, colour-vision safe) and `summary.md`; runs under one directory are labelled from `output/uq.csv`. Code in `pism_terra.profile_analysis`.
- `campaign.profile = true` saves PETSc profiling data for every `pism` leg the glacier and ISMIP7 runners generate: PISM's `-profile` is pointed at `<output>/profile/profile_<tag>.py`, `<tag>` being the leg's state-file tag, so ensemble members and init/forward legs keep separate files. `pism_terra.profiling` reads them: `load_profile` / `load_profiles` flatten PETSc's `ascii_info_detail` script (which cannot be imported, as PETSc assigns into events it never declared) into one row per stage, event and rank, and `event_summary` reduces a stage over the ranks to the slowest and fastest rank, their ratio (load balance) and the share of the stage, the numbers PISM's `pism_plot_profiling` draws.
- The importance-sampling page of `pism-s4f-report` explains how the joint posterior is formed: per-glacier log-likelihoods summed over the members every glacier has, with each glacier's weight set by the likelihood reduction, and a small table of cells with observations, decorrelation length, block side and independent blocks per glacier, which under the default `blocks` reduction is each glacier's weight in the sum.
- `pism-glacier-sensitivity-indices RUN_DIR --output-path OUT [--target ice_mass]` computes, for every glacier complex of a project with processed `scalar_C_*`/`scalar_G_*` files, the first-order Sobol and Borgonovo delta indices of the target's yearly-averaged time series to the UQ parameters (SALib's given-data estimator, which needs no special sampling design), per complex and per glacier of the complex, with bootstrap confidence bands, on a process pool with BLAS pinned to one thread per worker. Outputs mirror the importance sampling: NetCDF, CSV and one time-series figure per glacier under `<rgi_id>/`, `sensitivity_indices_summary.csv` at the top level. `pism-sensitivity-indices FILES...` runs the same analysis on one set of files. The shared code lives in `pism_terra.sensitivity`; `pism-s4f-report` gets a Sensitivity indices page and a `--target` option. SALib and threadpoolctl are new dependencies.
- Developer docs page `output_format.md`: how the 1 to 4 hour spread between UQ members was traced to PISM's `netcdf4_parallel` output path on Lustre, the per-node measurements behind the switch of the s4f configs to `netcdf4_serial`, why the ISMIP7 configs keep the parallel format, and what to change before writing ISMIP7 output monthly.
- `pism_terra.tools.chinook_node_io_test` also handles the ISMIP7 ice-sheet scripts: the writer launch (`pism_ismip7_writer -r 1`), task counts and partition are read from the production script, multi-node jobs are given as `n31+n34`, per-variable spatial files keep their `{var}` placeholder, `--years` shortens the leg from the script's own start date, `--bench-grid` sizes the netCDF benchmark, and an `async_nc4s` variant tests the production writer with PISM's own files in serial NetCDF-4.
- `pism-s4f-report RUN_DIR --output-path REPORT [--data-path] [--usgs-data-path]` runs `pism-glacier-importance-sampling`, `pism-glacier-usgs-benchmark-glaciers` and `pism-glacier-usgs-benchmark-stakes` into sub-directories of the report and renders `index.html` plus one page per tool (summary tables, joint posterior, every glacier's figures and member tables) in the layout of the pism-terra docs, with the Snow4Flow logo (a vector recreation ships with the package; `--logo` takes the official file). A tool that fails is shown with its traceback instead of stopping the report; `--skip` and `--no-run` control what runs.
- `python -m pism_terra.tools.chinook_node_io_test generate RUN_SCRIPT --nodes ... --test-dir ...` pins a shortened copy of a production forward leg to named chinook nodes in three output variants (`async` with `pism_async_writer`, `sync`, `noout`) and times, per node, the container's Python imports, a `dd` write, a netCDF append benchmark and the forward leg; `analyze TEST_DIR` tabulates seconds per model step by node and variant. Written to track down the September 2026 UQ runs whose wall time varied 3 to 6 times between nodes with identical solver work while the asynchronous writer lagged the model.
- The xarray likelihoods (`log_normal_xr`, `log_pseudo_huber_xr`) take `reduction="mean"|"sum"|"blocks"` and `block_size` (`pism_terra.likelihood.reduce_log_likelihood`): `mean` averages the cells (the previous behaviour, which the docstring wrongly called a sum; it tempers the posterior by the cell count, so gridded fields barely separate the members), `sum` treats every cell as independent (right for a time series, as in the pism-emulator `calibrate-as19.py`), and `blocks` sums one independent sample per `block_size` x `block_size` cells. `importance_sampling` forwards them through `likelihood_kwargs`.
- `pism-glacier-importance-sampling RUN_DIR [--data-path] [--output-path]` importance-samples every glacier UQ ensemble of a project against its observed elevation change: per glacier, likelihood weights, resampling counts and effective sample size for each `--fudge-factors` value, a plain and a block-bootstrap RMSE ranking with the members statistically tied with the best, posterior histograms of the UQ parameters (from the run's `uq.csv`, prior outlined), a NetCDF and CSV per glacier under `<rgi_id>/`; a joint posterior over all glaciers under `joint/` (the members are shared parameter draws, so their per-glacier log-likelihoods add up); and `importance_sampling_summary.csv` / `importance_sampling_weights.csv` at the top level. `--variable SIM:OBS[:OBS_STD]` (repeatable) evaluates other fields; `--no-bootstrap` skips the ranking. Holes in the observations are skipped and the summary reports each glacier's valid-cell coverage.
- `pism_terra.calibration` collects the calibration building blocks the KITP driver used to keep to itself: the decorrelation length, the streaming block-bootstrap RMSE and a `rank_by_bootstrap_rmse` wrapper (tied set within the 5-95% interval), `observation_uncertainty`, `importance_weights` (now with `obs_var`/`obs_std_var`/`sum_dims` and a `log_likelihood` output), `weights_from_log_likelihood`, `joint_log_likelihood`, `posterior_table` and `plot_parameter_histograms` (with a prior outline). All accept any member dimension (`exp_id`, `uq_id`). `pism-kitp-calibrate` is unchanged in behaviour and re-exports the names.
- `importance_sampling` no longer interpolates the ensemble onto the observed grid; the caller aligns them (`simulated.interp_like(observed)`) and mismatched coordinates raise a `ValueError`. This keeps the function out of the way of pint-xarray's `PintIndex`, which plain `interp_like` cannot read. When pint-xarray is installed and the input is quantified, the simulated variable and the observed uncertainty are converted to the units of the observed mean before the likelihood; without pint-xarray, or with plain arrays, nothing changes.
- `pism-glacier-run` / `pism-glacier-run-inverse` copy the config TOML (and the PISM CDL when given), the job template and the UQ file into `<output-path>/config/`, `templates/` and `uq/`, and generate the run scripts from those copies. The directories were created before but only filled for files downloaded from S3 or HTTP; local and package files left them empty. An unchanged file is not re-copied; a changed one replaces the snapshot with a notice.
- `pism-ismip7-greenland-observations` prepares the observed Greenland mass balance a run is validated against: the GRACE Tellus ice-sheet time series, and Mankoff et al. (2021) per Mouginot region plus a `GIS` total on the source's `region` dimension. `pism-ismip7-greenland-stage` now prepares them as part of staging, caching under the shared `--data-path` so downloads happen once rather than per run, and copying the two products into `<output-path>/output/observations/`; `--no-observations` skips it. Failures there are logged and staging continues — the GRACE Tellus product needs an Earthdata login and these are validation data, not run inputs. Ported from `pism-ragis`'s `03_prepare_mass_balance.py` onto pism-terra's caching downloads; the PO.DAAC collection is the current `RL06.3_V4` (RL06.1_V3 is retired) and its header is found rather than assumed.
- The PISM-Cloud notebook's **Live run log** carries a progress bar under the log, with the model date beside it. It reads PISM's own `S 1986-03-21 21.836h:` stamps against the `-time.start` / `-time.end` the run script echoes under `bash -ex`, so nothing extra has to be published and no config lookup is needed (`run_progress` in `notebooks/pism_cloud_app.ipynb`). Those flags are emitted sorted, so `-time.end` precedes `-time.start` and they are matched by name; a multi-leg run takes the last pair seen and so tracks the leg running now rather than mixing an init leg with the forward one.
- `pism-glacier-execute` publishes the run script's output to S3 while the run is going, so the PISM-Cloud notebook can show live progress to people who have only an Earthdata login. It tees the script's combined output to `<RGI dir>/logs/progress.log` and a background thread copies that to `s3://{bucket}/{bucket_prefix}/{rgi_id}/logs/progress.log` every 30 s, tagged `file_type=log` rather than `file_type=product` (`execute.ProgressPublisher`). Everything still goes to stdout, so the CloudWatch stream stays complete; publishing is best-effort and an S3 failure never stops the simulation; the final publish happens on the way out even when the script fails, which is when the log matters most. `notebooks/pism_cloud_app.ipynb` gains a **Live run log** section that tails it with `s3fs(anon=True)` — the same public read path step 6 already uses for the run scripts.
- `pism-ismip7-greenland-prepare` takes `--gcm`, `--pathway` and `--forcing` to narrow the `forcings` step to part of the tree, so a variable that appears upstream can be picked up without regenerating all 22 forcing files (`forcing.select_forcing_tasks`). Each accepts a comma-separated, case-insensitive list; a selector that matches nothing is an error rather than a no-op run. Used to rebuild the two CTRL2015 climate files after `mrro` was published under `ctrl` on 2026-09-11: `--include forcings --pathway ctrl --forcing climate`.
- `[campaign.forcing_versions]` pins the ISMIP7 forcing-file versions per GCM, e.g. `CESM2-WACCM = {climate = 3, ocean = 2}` — the same numbers as `[gcms.<GCM>.source]` in `setup_ismip7_greenland.toml` (integers, `"3"` or `"v3"` are all accepted). When the `[inverse]` table requests an alternating tauc/hardav inversion (`inverse.alternating_cycles > 0`) or a hardness inversion (`inverse.design.variable = "hardav"`, or the short option `inv_design`), the forward `pism` leg regrids `tauc,hardav` from the inversion output and sets `stress_balance.averaged_hardness.enabled`, so the Blatter solver uses the inverted column-constant hardness instead of the enthalpy-derived one (`pism_terra.inversion.inversion_uses_hardav`). Requires a PISM with that option (dev branch, September 2026).
- `pism-kitp-calibrate` importance-samples every field again, next to the block-bootstrap ranking. Each member gets a Gaussian likelihood weight from its misfit (`pism_terra.filtering.importance_sampling`), for the fudge factors in `--fudge-factors` (default `1,3,10`); the RCM fields carry no uncertainty, so `observation_uncertainty` supplies `max(--relative-error × |obs|, --error-floor)` (defaults 10 % and 50 kg m^-2 yr^-1 — the floor keeps near-zero cells from being infinitely informative, which is what the old `1e-8` did). Per field it prints the effective sample size `1/Σw²` and the top member, writes `<ebm>_<var>_importance.csv` (weights and counts per fudge factor joined with the parameters) and one parameter-histogram figure per fudge factor. `--n-samples` (default 10 000) only sets the resolution of the resampled histograms — the share of a member with weight *w* has standard error √(w(1−w)/n) — so it no longer follows the ensemble size.
- `pism-glacier-usgs-benchmark-stakes` compares the USGS benchmark-glacier *stake* measurements with PISM. For every glaciological site in the release it samples the run's monthly `spatial_*.nc` output at the stake's location (nearest cell by default, `--method linear` for bilinear) and integrates the modelled surface mass balance — `surface_accumulation_flux − surface_runoff_flux`, or the per-cell `tendency_of_ice_mass_due_to_surface_mass_flux` when those are absent — over exactly the interval each measurement covers: the previous fall visit to the spring visit for `bw`, spring to fall for `bs` (observed as `ba − bw`), and between the two visits for a sub-seasonal `db`. Cells the model has deglaciated give NaN rather than a spurious zero balance. Per glacier it writes one figure with a panel per site (sorted by elevation), a modelled-vs-observed scatter, balance-against-elevation gradient plots per season (observed filled, modelled hollow) with a two-piece linear fit for each — one slope below and one above an ELA found by least squares, both pieces zero there, written to `usgs_benchmark_stakes_gradients.csv` — and a NetCDF of the series into a `<rgi_id>/` sub-directory, and per-site plus pooled skill scores (with the model's surface-elevation offset at each stake) into `usgs_benchmark_stakes_skill.csv`.
- `pism-glacier-usgs-benchmark` scores the model against the observations: Pearson r, mean absolute error and bias over the years both sides have, for the winter, summer and annual surface balances (when monthly output gives them) and for the annual balance against total `tendency_of_ice_mass`. Ensembles are scored on the median the plot draws; r is withheld below three overlapping years or for a constant series. The numbers go into a box on each figure, into `usgs_benchmark_skill.csv`, and as attributes on the saved model series.
- `pism-glacier-usgs-stakes OUTPUT.gpkg` writes the point measurements behind the USGS benchmark-glacier balances — seasonal `bw`/`ba` per stake and year, and the sub-seasonal `db` between visits where a glacier has them — to one GeoPackage (`sites`, `stakes`, `subseasonal` layers), in the release's m w.e. with the two date notations it mixes parsed into real date fields. Shares the download cache with `pism-glacier-usgs-benchmark`.
- `pism-glacier-usgs-benchmark` plots modelled winter and summer balances when the run has monthly output. A balance year runs from one annual minimum to the next and splits at the winter maximum, and the USGS release dates both per year (`Ba_Date`, `Bw_Date`), so the model is integrated over exactly the interval each observation covers — a month straddling a boundary is apportioned by days rather than snapped, since the measured dates fall mid-month more often than not. The integrated variable is `tendency_of_ice_mass_due_to_surface_mass_flux`, which is what a stake network measures; the existing annual line still shows total `tendency_of_ice_mass`. Years the release leaves undated, and seasons the model record does not fully span, are omitted rather than partially summed. Annual-only output is detected and leaves the plot unchanged. The seasonal series are saved alongside the observations as `Bw_model`/`Bs_model`/`Ba_model`.

Ensemble mode only; ignored without a `UQ_FILE`.
- `pism-glacier-usgs-benchmark` compares PISM with the USGS benchmark-glacier record. Given a run directory it overlays `tendency_of_ice_mass` from every `scalar_G_*.nc` below it — one line for a single run, median and 5-95 % band for several. Error bars are drawn when the CSV has an uncertainty column (none in v10) or `--uncertainty` supplies a constant.
- `[campaign] init_surface_model` lets the init leg run a different surface model from the main leg — e.g. `init_surface_model = "debm_enhanced_forcing"` to spin up with `surface.models = "debm_enhanced,forcing"` holding the geometry, then continue on plain `debm_enhanced`. An unknown name is rejected at render time with the available tables listed. Complements `init_climate`, which does the same for the forcing.
- A worked L-curve example for choosing the Tikhonov penalty weight, at `docs/source/greenland/inversion.md`. - UQ parameters can be **derived** from another instead of sampled: `derived_from` names the base and `scale`/`offset` give the relation (`value = base * scale + offset`). Physically linked options — a mass-balance profile whose melt limits and ELA shift together — stay linked in every ensemble member. Writing them as parallel `choices` lists could not do this: Latin Hypercube permutes each column independently, so the lists came out misaligned. Derived values are computed after sampling, so the base may be categorical or continuous and a derived parameter may itself be another's base; unresolvable bases, cycles and specs declaring both a `distribution` and a `derived_from` are rejected at load. Wired into the glacier, ISMIP7 Greenland and KITP ensemble builders. `pism_terra/uq/kennicott_elevation_dependent.toml` now samples only `z_M_min` and derives the other two.
- `[bed_deformation]` and `[frontal_melt]` are optional. `PismConfig` required both, so 29 of the packaged glacier configs — every `rgi_*`, `kennicott_*` and `s4f_carra2*` file — failed `load_config` outright with `bed_deformation Field required`, taking `pism-glacier-stage` and `pism-glacier-run-*` down with them. - Glacier runs can prepend an init leg, the capability the ISMIP7 Greenland runner already had. `[campaign] init_start` / `init_end` make `pism-glacier-run-forward` and `-run-inverse` emit a bootstrap run over that span first; the main leg then restarts from its state file instead of bootstrapping itself. Init products are named for the init span, so they do not collide with the main leg's. Without the two keys nothing changes.
  A new `[campaign] init_climate` names a second climate builder used by the init leg alone — e.g. `init_climate = "carra2-monthly-mean"` to spin up on a climatology and then continue on transient CARRA2. `stage` builds both forcings and the run generator substitutes the init one into `atmosphere.given.file`, `surface.debm_simple.{std_dev,albedo_input}.file` and `surface.pdd.std_dev.file` for that leg. The glacier templates gained a guarded `run_init_str` slot.
- `carra2-monthly-mean`, a CARRA2 monthly climatology, as the counterpart of `era5-monthly-mean`. Twelve fields, one per calendar month, on the periodic 365-day `days since 0001-01-01` axis with `time_bounds` tiling the year, so PISM cycles it for the length of the run. `pism-glacier-prepare` does the averaging once into `climate/carra2_monthly_mean.zarr` (shared, like the store it comes from) and pre-reprojects it per aggregate group as `climate/carra2_monthly_mean_<group>.nc`; `stage` fetches the group file when it exists and otherwise clips the store directly. Select it with `climate = "carra2-monthly-mean"`.
  The reference period is **fixed** at 1990-2019 (`CARRA2_CLIMATOLOGY_YEARS`) rather than "everything in the store", so extending the CARRA2 download later does not silently change the climatology, and it stays comparable with the ERA5/RACMO/MAR means over the same years. `air_temp_sd` is averaged like every other field and so remains the typical *within-month* variability that PISM's PDD scheme reads — not the year-to-year spread of the monthly means.

  ```text
  <OUTPUT_PATH>/input/{gebco,heatflux,climate}/     # global — written once
  <OUTPUT_PATH>/input/<project>/rgi/<project>_{c,g}.gpkg
  <OUTPUT_PATH>/input/<project>/ice_thickness/{frank,maffezzoli}/
  <OUTPUT_PATH>/input/<project>/climate/carra2_<group>.nc
  ```

  The split follows the `[regions]` `crs` overrides. Those change the *contents* of the RGI GeoPackages and the ice-thickness rasters without changing their paths, so an S4F run and an RGI run previously overwrote each other's `ice_thickness/frank/RGI2000-v7.0-C-01/*_thickness.tif` and `rgi/rgi_c.gpkg`. Everything that does not depend on a CRS override — GEBCO, heat flux, SNAP, the merged `carra2.zarr` — is now stored once rather than per project, and `staging/` stays shared so the raw downloads are not fetched twice.
  **Migration:** campaign configs gain `project_directory` alongside `prefix`, which now names the shared root: `prefix = "rgi/glacier"` becomes `prefix = "glacier/input"` + `project_directory = "rgi"`, and the S4F configs also switch to `rgi_complex_file = "s4f_c.gpkg"` / `rgi_glacier_file = "s4f_g.gpkg"`. Readers of project-specific data (outlines, ice thickness, per-group CARRA2) address `{prefix}/{project_directory}/…`; readers of global data keep using `{prefix}/…`. Campaigns that leave `project_directory` unset — ISMIP7, KITP, ML — are unaffected, since the two prefixes then coincide. The S3 tree has to be rearranged to match before the new configs resolve; the old `rgi/glacier/…` and `s4f/glacier/…` trees can stay in place until the cutover is confirmed.
- Post-processing is now two campaign-neutral modules, `pism_terra/postprocess_scalar.py` and `pism_terra/postprocess_spatial.py`, exposed as `pism-postprocess-scalar` and `pism-postprocess-spatial`. They serve Greenland basins and RGI glaciers alike: the CRS is read from the file's grid mapping instead of assuming EPSG:3413, outlines are reprojected onto it (RGI ships EPSG:4326), the label column is resolved from `glacier_id`/`rgi_id`/`SUBREGION1`, the region dimension is `--dim-name` (default `glacier_id`), the whole-domain total is opt-in via `--total-name`, and each region carries its outline `area`. **Removed:** `pism-ismip7-greenland-postprocess`, `pism-ismip7-greenland-postprocess-spatial` and `pism-kitp-postprocess` — regenerate run scripts, or call `pism-postprocess-scalar ... --total-name GIS`. `pism-glacier-postprocess` is unchanged.
  **Migration:** every campaign, Greenland included, now writes the region dimension as `glacier_id` and labels basins from the outline's `glacier_id` column (`GIS_CE`, `GIS_CW`, …) rather than `basin`/`CE`. Selection becomes `ds.set_index(glacier_id="glacier_id_name").sel(glacier_id="GIS_CE")`; the appended whole-ice-sheet total is still `GIS`. Analysis code that hard-codes the old names — `pism_terra/analyze_scalar.py`, `pism_terra/kitp/analyze.py` — has not been updated and will need it. Pass `--column SUBREGION1 --dim-name basin` to reproduce the previous naming.
- `glacier.execute` no longer accepts a `--job-id` parameter and now stages files based on the full S3 URI of `RUN_SCIPT`, if needed.
- Per-region scalar output (ISMIP7 Greenland, KITP, and glacier post-processing) is now readable by CDO: `time` is written as the first dimension, and the region dimension (`basin` / `RGIid`) is a positional integer index whose labels live in a companion `basin_name` / `RGIid_name` coordinate. **Migration:** label selection now needs `ds.set_index(basin="basin_name").sel(basin="GIS")`. Previously CDO refused these files outright with `Time must be the first dimension!` followed by `Unsupported file structure`.

### Fixed
- `pism-postprocess-spatial` failed with `MissingCRS` on a PISM file with no integer field, such as an output whose `mask` is written as a float. The basin files were stamped with the optional `crs` override rather than the projection read from the input, so without an override they relied on a CRS the subset already carried -- and masking strips PISM's `grid_mapping` pointer to `mapping` from every float field. They are now stamped with the projection read from the input.
- The ISMIP7 Core projections ran one year short. A counter sets `time.end` from the experiment table, and it used January 1 of the last forcing year, so C007 stopped at `2300-01-01` with the `..._2015_2300.nc` forcing still holding a year, and its products were named `2015-2299`. `proj_end_year` and `campaign.projection_end_year` now mean the last year simulated: the run ends on January 1 after it (`2301-01-01`, `2101-01-01` for ssp370) and the products are named `2015-2300`. C011 (OCX) is unchanged at `2025-01-01`. The `c003`-`c008` and `c010` configs name the last year again (`2100`/`2300`); with a counter set that entry is overridden either way. The PPE configs (`ismip7_greenland_ppe_ssp126/370/585.toml`) have no counter and state `time.end` themselves; it moves to `2301-01-01` (`2101-01-01` for ssp370) to match.
- A UQ file that mixed quoted dotted headers (`['calving.thickness_calving.threshold']`) with unquoted ones (`[fracture_density.softening_lower_limit]`) was rejected with `UQ entries declare neither 'distribution' nor 'derived_from': ['fracture_density']`: one dotted key made the whole file be read as dotted, so the nested table was taken for an entry named after its first component. `UQConfig` now reads each top-level key in its own spelling.
- `pism_terra.ismip7.greenland.mass_balance` no longer runs out of memory integrating a large ensemble over the basins (the 2026-10 plume ensemble, 3 GCMs x 6 pathways x 315 years at 1 km, was killed on a 16 GB JupyterHub, with or without Dask workers). `regional_sums` reduces every chunk that holds the whole grid to its basin integrals in a single task (`basin_block`) instead of a dozen linked tasks per chunk, and `open_submission` pads the runs onto the common time axis and pathways with lazy NaN blocks (`onto_labels`) instead of an xarray `reindex`, which built masks as large as a whole variable and read real data only to mask it out. The integrals are accumulated in float64. Chunks that split the grid in `y` or `x` take the previous masked contraction.
- `pism_terra.ismip7.greenland.mass_balance` splices the control runs (C009/C010, pathway `ctrl`) onto their GCM's historical run like the SSP projections. The control run starts in 2015 from the historical state; left on its own it had no record in the reference year (1990 by default), so its cumulative mass balance was missing throughout and the figures drew no `ctrl` line.
- `render_terrain_3d` no longer draws a black outline around the glaciers in some frames. The ice overlay keeps every cell with ice at any corner, so at the margin it reaches points with no ice, where the overlay variable (e.g. `velsurf_mag`) is missing; their colormap "bad" color came out black. Such points now show the terrain beneath (transparent under `--shading lit`). It showed in summer frames, when the margin thins to no ice next to ice.
- `pism_terra.ismip7.greenland.mass_balance.compute_regions` (and `pism-ismip7-greenland-mass-balance`) computes the basin integrals one flux at a time. In a single graph Dask read far ahead on some fluxes before finishing the others: on the 2026-10 plume ensemble, with C006 running to 2299, the step held 23-27 GB and the notebook kernel was killed; flux by flux it holds 3 GB, in the same time and with identical results. The basin masks are still built once.
- `pism_terra.ismip7.greenland.mass_balance` decodes the submission's time axes to `datetime64[s]`. A run past 2262, such as the 2015-2299 extension C006, does not fit nanosecond dates and came back as cftime while the rest stayed datetime64, so the combined ensemble had a time axis of two types that cannot be compared, and building the regional series failed.
- The CalFin retreat masks no longer carry a `GeoTransform` on `spatial_ref`. Older rioxarray writes one in `write_crs` with `dy > 0`, following the ascending y of `create_domain`; GDAL prefers it over the y coordinate, so QGIS drew the masks upside down. PISM was unaffected, as it reads the coordinates.
- The progress bars of the analysis tools (`pism_terra.progress`) are drawn in Jupyter notebooks as well: the check for a terminal turned them off there, since ipykernel's standard error is not a tty, so `compute_regions` and the importance-sampling steps ran silently in `ismip7-analysis.ipynb`.
- `pism-ismip7-greenland-mass-balance` zeroes the cumulative mass balance at 1990 by default instead of 1985. The OCX run starts in 1990, so with a 1985 reference it had nothing to subtract and its cumulative series came out missing throughout.
- `pism-ismip7-greenland-mass-balance` splices the historical run only onto the `ssp*` projections (`splice_historical(..., projections=r"ssp\d+")`). It was also copied into every GCM's OCX pathway, which only the OCX run has, so the figures showed `MRI-ESM2-0 OCX` and `CESM2-WACCM OCX` lines (the historical run under another name) beside the real one, which is now labelled plain `OCX`.
- `pism-ismip7-greenland-mass-balance` prepends each GCM's historical run to its pathways before integrating (`compute_regions(..., splice=True)`, on the regional series rather than the gridded ensemble), so a pathway's cumulative mass balance runs from the reference year through the projection instead of starting in 2015 with the historical years missing. `splice=False` keeps the pathways as run.
- `pism-ismip7-greenland-mass-balance` no longer carries a run's last cumulative mass balance forward as a flat line over the years it has no records for (a run still in flight, or a shorter pathway outer-joined onto the ensemble's time axis): the cumulative series is missing wherever the mass balance is, so the plots stop where the data stop.
- `pism-ismip7-greenland-run-forward` / `-inverse` failed on PISM-Cloud with `FileNotFoundError: 's3:/pism-cloud-data/...'`: the config, template, UQ and CDL arguments went straight into `Path`, which collapses the `s3://` double slash. The ISMIP7 runner now downloads remote project files and snapshots every project file under `<output-path>/config/`, `templates/` and `uq/` before use, as the glacier runner has done since the snapshot change, and uploads its output tree with `--bucket`/`--bucket-prefix`, which it accepted but ignored.
- `preprocess_netcdf` reads the ensemble member id from the file name only. It searched the whole path, so in a project directory named `..._uq_50` every file got `uq_id = 50` and `open_mfdataset` failed with "Could not find any dimension coordinates to use to order the Dataset objects for concatenation", which broke the importance sampling and the sensitivity indices there. The experiment and GCM ids still fall back to the path (the ISMIP7 submission tree keeps the counter in a directory) and the RGI id to the `command` attribute.
- The forward leg after an inversion regrids exactly the fields the inversion wrote, following `inverse.design.variable` as `pismi` does (`tauc`, `hardav`, or both for `tauc_hardav` / `hardav_tauc`), held fixed with the constant yield-stress model and, when `hardav` is among them, the prescribed Blatter hardness. Previously a positive `inverse.alternating_cycles` alone made the leg ask for `hardav`, which a `tauc` inversion never writes, so every s4f run died at the forward leg with "Can't find variable 'hardav'" once the configs carried `alternating_cycles = 1`. Both glacier and ISMIP7 generators share the wiring in `pism_terra.inversion.forward_leg_from_inversion`.
- `pism-ismip7-greenland-run-forward` and `-run-inverse` stage the observed mass balance into `<output-path>/output/observations/` like `pism-ismip7-greenland-stage` does; only the stage command's own CLI ran that step, so a run generated directly had no observations to validate against. `--no-observations` skips it.
- A single-leg run with ISMIP7 naming no longer emits a `pism-postprocess-scalar` command that cannot run. The ISMIP7 tree's `output.spatial.file` is a `{var}` pattern PISM expands into one file per variable, and `pism-postprocess-scalar` opens its input with `xr.open_dataset`, so the generated command pointed at a path with a literal `{var}` in it. Those runs get `pism-ismip7-postprocess-flux` over the submission directory instead, which is where their per-basin numbers were already coming from; a single leg with ISMIP7 naming off still gets the scalar step on its combined spatial file.
- The ISMIP7 Greenland init leg now runs the config's `[bed_deformation]` model. It was left out of that leg (a leftover from when it was only the inverse prior), so with the Lingle-Clark model every counter config wrote an init state without `viscous_bed_displacement`, and the historical leg, which *restarts* from it rather than bootstrapping, died with `Can't find 'viscous_bed_displacement'`. Regenerate init states written before this change; the `_base_run_dict` switch is gone.
- Cloud Optimized GeoTIFFs are written through GDAL's CreateCopy again. GDAL 3.13 added a `Create()` entry point to the COG driver, so rasterio ≥ 1.5.1 on that GDAL routes `rasterio.open(..., "w", driver="COG")` — and rioxarray's `to_raster(driver="COG")` — through it, and that path drops band descriptions and writes NaN nodata pixels as 0. The Hugonnet dh mosaics came out with `(None, None)` bands and zeros where there were no observations, which is what the CI failures in `test_dh_observations` were. Every COG write (dh mosaics and planning COGs, the Frank and Maffezzoli thickness mosaics, the GEBCO bathymetry) now goes through `pism_terra.raster.cog_writer` / `write_cog`: a tiled staging GeoTIFF next to the target, copied into the COG with `rasterio.shutil.copy(driver="COG")` and removed afterwards, also on error. Behaviour on GDAL ≤ 3.12 is unchanged.
- `prepare_carra2` no longer fails with `NetCDF: HDF error` on workstations whose `/tmp` is a RAM-backed tmpfs. The yearly CARRA2 batches were merged with `cdo mergetime` into a temporary NetCDF in `$TMPDIR` — the whole 1986-2025 record, ~57 GB compressed — which overflowed a 62 GB tmpfs, and the merged file was then read back and written a second time into `carra2.zarr`. The batches are now concatenated lazily with `xr.open_mfdataset` and written straight into the store, one band of rows at a time (`write_zarr_in_bands`), so the record is written once and peak memory is one band rather than the rechunk of the whole domain. CDO scratch for the remaining small steps goes next to the batches instead of `/tmp`.

- The project's RGI GeoPackages are fetched once per data path, not once per glacier. `stage_glacier` and `s4f_glacier` cached them under each glacier's own `staging/` directory, so `pism-s4f-planning` — which walks every glacier in the project — re-downloaded the 309 MB S4F pair for each one and kept a copy: 4.6 GB of identical files after only 16 glaciers. Both now take an `rgi_cache_path`, and the CLIs pass the shared `--data-path` root. The outlines describe the whole project, so one copy serves every glacier. Existing per-glacier copies are harmless but can be deleted.
- Staging no longer aborts when a glacier's domain overhangs an ITS_LIVE tile edge. `region_code_from_bounds` required a per-region COG to *fully contain* the requested bbox, and a staged domain is the glacier plus a buffer plus a 0.25°/0.1° geographic pad — so `RGI2000-v7.0-C-03-01124` (northern Ellesmere) failed with "No ITS_LIVE per-region COG fully contains bounds" even though the glacier itself is 100 % inside region `03`; the domain reached 17 km past the tile's northern edge. The region is now taken from the RGI ID when available and the containment requirement is a preference: partial coverage is used and the shortfall logged. The overhang interpolates to NaN and is zeroed, which the velocity code already did for ITS_LIVE's own nodata gaps.
  Deriving the region from the ID also removes a genuine ambiguity — the footprints overlap in polar stereographic, and that Ellesmere domain sits inside the Arctic Canada (`03`) and Greenland (`05`) footprints by *identical* amounts, so the old geometry-only search picked whichever came first in the probe order.
- The apptainer job scripts honour a container passed in from the submitting environment. `container=/path/to/other.sif sbatch <script>` reached the job — SLURM's default `--export=ALL` carries it — but the script then discarded it on line 20 with an unconditional `export container=$HOME/pism-ismip7.sif`, so every run silently used the default image. It is now `export container="${container:-$HOME/pism-ismip7.sif}"`, and the not-found message shows the override syntax. Applies to all five apptainer templates; re-render existing run scripts to pick it up.
- CARRA2 forcing files carry a CF `grid_mapping` attribute again. `_finalize_pism_crs` stamps it, but rioxarray records `grid_mapping` in each variable's *encoding*, and handing `to_netcdf` a per-variable `encoding` dict for compression **replaces** that encoding rather than merging into it — so the attribute never reached the file and the written NetCDF had no discoverable projection. It went unnoticed because the per-glacier file is reprojected onto the model grid, where PISM does not need the projection; a per-group cache, which PISM must reproject itself, would have been rejected with "computational domain is not a subset". A new `pism_terra.workflow.compressed_encoding` builds the encoding while carrying `grid_mapping` through, and the three CARRA2 write sites use it. Re-run staging to fix existing files; nothing else changes in them.
- CARRA2 staging no longer stacks the time-invariant `orography` field once per output year. `_carra2_fill_years_and_bounds` concatenated its per-year pieces with xarray's default `data_vars="all"`, which broadcast orography across the whole time axis only for the next block to drop the copies; it now passes `data_vars="minimal"` explicitly. Output is unchanged, and xarray's `FutureWarning` about the changing default is gone.
- `pism-glacier-prepare` exits 0 on success. Its entry point pointed at a function returning a `dict`, which setuptools passed to `sys.exit`, so a completely successful run printed the dict to stderr and exited 1.
- Per-region scalar output no longer carries a CF grid mapping. A summed timeseries has no grid, but the dimensionless `mapping` (or `spatial_ref`) variable survived the reduction over `x`/`y` and every variable pointed at it through `coordinates = "glacier_id_name mapping"`. Dropping it before the reduction was not enough — `rio.write_crs` recreates it from the dataset's own grid-mapping name — so it is now stripped from the result. Affects `pism-postprocess-scalar` and `pism-glacier-postprocess`; the spatial post-processing keeps its grid mapping, which it needs.
- `normalize_timeseries` no longer fails on a single-element variable list. `ds[["a"]] -= ...` takes a different `__setitem__` branch than a longer list and raised `cannot directly convert an xarray.Dataset into a numpy array`, so a bare string and a two-variable list worked while `["a"]` did not.
- `pism-kitp-analyze` reads the current post-processing output again. It assumed a `basin` dimension carrying string labels; scalar files now use the `glacier_id` integer index with labels in `glacier_id_name`. `with_region_labels` normalises all three layouts it has produced over time — `glacier_id`, `basin`/`RGIid`, and raw PISM scalar files with no region dimension — so selection by region name works regardless of file age. Two long-standing bugs fell out: the per-cell area used to convert grounding-line flux was hard-coded to 900 m (rescaling every other resolution by `(dx/900)²`, e.g. 1.78× at 1200 m) and is now read from the run's `grid.dx`; and `grounding_line_flux_nonneg`, which only post-processed files carry, is omitted with a log line instead of raising `KeyError` on raw scalar input.
- Region labels (`glacier_id_name`, and `basin_name` / `RGIid_name` when those dimension names are used) are written as a NetCDF char array instead of the netCDF-4-only variable-length `NC_STRING`. ncview rejected the whole file with `netcdf_fi_get_data: error on nc_get_vara_float call ... NetCDF: Not a valid data type or _FillValue type mismatch`. The labels still read back as strings, so label-based selection is unchanged; re-run post-processing on files that need to open in ncview.
- `pism-ismip7-greenland-postprocess` / `pism-kitp-postprocess` accept a directory as `OUTFILE` and name the file `basin_<input>.nc`, following the run scripts' convention. Passing a directory previously ran the whole reduction and then died in `to_netcdf` with `PermissionError: ... /output/basins`, losing the work. An unwritable destination is now reported before the reduction starts, and the log is written next to the output file.
- glacier post-processing now derives `ice_mass_glacierized` too, so the per-RGI scalar output carries the same diagnostic as the basin post-processors (only when the input has both `ice_mass` and `thk`).
- `ice_mass_glacierized` (ISMIP7 Greenland and KITP basin post-processing) now takes its ice-free threshold from the run's own `output.ice_free_thickness_standard` instead of a hard-wired 10 m, so a config that overrides the standard is summarised with the value the simulation used. Falls back to 10 m — PISM's default — when the file carries no `pism_config`.
- `pism-kitp-calibrate` no longer materialises the whole ensemble to rank it. The block-bootstrap RMSE is now a streaming `coarsen` reduction (`squared_error_blocks`), so peak memory is set by the dask chunk size rather than by `n_exp × ny × nx`, and only the metric's four variables are carried through the conservative regridding. Measured on an 8-member ensemble: 68 s → 27 s, with bit-identical RMSE.
- basin post-processing no longer fails with `Object has inconsistent chunks along dimension time` on files whose spatial variables differ in dtype
- basin rasters are scattered to the Dask workers instead of being embedded in the task graph, removing the `Sending large graph of size ...` warning on fine grids
- `spatial_ref` and other CF grid-mapping variables are dropped before the per-basin merge, which previously failed with `unable to determine if these variables should be coordinates or not`
